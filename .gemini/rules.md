# TraceApp プロジェクト開発・コーディング原則

本ドキュメントは、TraceApp (PyTrace) の開発における絶対的な設計原則、コーディング規約、運用制約、および自律改善ルールを定義したものです。本プロジェクト内のすべてのコード変更およびエージェントの動作は、以下のルールに厳格に従う必要があります。

---

## 1. 言語およびドキュメンテーション規約
- **対話・説明言語**: ユーザーとの対話、実装計画、タスク、Walkthrough、Git操作の説明文はすべて**日本語**で記述すること。
- **コード内コメント**: 関数・クラスのJSDoc、型定義の説明、インラインコメント、テストケースの説明文を含め、コード内のコメントはすべて**日本語**で記述すること。
- **命名規則**: 変数名・関数名・クラス名は明確で分かりやすい**英語**で命名すること（ローマ字命名は禁止）。

---

## 2. アーキテクチャおよびコーディング原則
- **単一責任の原則（SRP）**: 各関数・コンポーネントは1つの明確な責務に集中させること。
- **関数の行数制限（目安30〜50行）**:
  - 各関数・コンポーネントは**30〜50行以内を目安**に適度に分割すること。
  - 巨大な関数（100行以上）を放置せず、構文解析、コード変換、フォーマット出力などの機能単位で小さな純粋関数に分離すること。
- **TypeScriptの型安全性**: `any` の乱用を禁止し、厳格な型付け（Interface/Type）を行うこと。
- **ポータブル・オフライン前提設計**:
  - `dist/index.html` に単一ファイルバンドル（`vite-plugin-singlefile`）され、完全オフラインで動作する構成を維持すること。
  - 外部ネットワークへの依存や動的ファイル分割による実行時エラーを生じさせないこと。

---

## 3. 重要な運用・プロセス制約（厳守事項）
- **並列プロセスの多重起動禁止**:
  - 開発サーバー（`npm run dev`, `npx vite` 等）は同時に1つだけ起動すること。
  - ビルドコマンド（`npm run build`）も同時に複数実行しないこと。
  - コマンド実行時は既存プロセスの状態を確認し、バックグラウンドでの無駄な重複起動を防ぐこと。

---

## 4. ドメイン機能・仕様の基本原則
1. **トレースエンジン (Pyodide)**:
   - メインスレッド上での単一インスタンスによる事前一括実行（`sys.settrace()`）方式。
   - 10,000ステップ上限ガード（`TraceLimitExceeded`）、特殊値（NaN, Infinity, 循環参照）のサニタイズを維持すること。
2. **コードエディタ (Monaco Editor)**:
   - Python および マクロ言語（VBA）のシンタックスハイライト、実行行デコレーションハイライトを連動させること。
   - マクロ言語（VBA）の構文キーワード（`If`, `Then`, `ElseIf`, `Else`, `End If`, `Do While`, `For`, `Sub`, `Function`, `MsgBox` 等）はすべて統一されたキーワード色（青色）としてハイライトすること。
3. **Python ⇄ マクロ言語（VBA）相互変換**:
   - メイン処理を `Sub Program() ... End Sub` で囲み、4スペースインデントすること。
   - 関数外の変数は `Dim <var> As <Type>` として `Sub Program()` の直下に一括宣言し、1行空白行を空けてメイン処理を記述すること。
   - `def` 関数は `Sub Program()` の外側に独立した `Function` / `Sub` として配置し、引数および戻り値の型宣言（基本型 `Integer`）を付与すること。
   - `print(...)` は `MsgBox (...)`（半角スペース＋括弧）に変換すること。
   - `for i in range(1, 4):` のような数値指定は、計算後のシンプルな `For i = 1 To 3` として出力すること。
4. **流れ図生成 (AST)**:
   - 順次（長方形 `5 → a`）、判断（ひし形、数学記号化 `＝`, `≠`, `≧`）、繰り返し（六角形）、共通水平合流線のレイアウト原則を維持すること。

## 5. ドキュメントおよびルールの自律的・継続的アップデート
- **プロジェクトドキュメントの同期更新**:
  - 新機能の追加、仕様変更、画面レイアウトやUIの変更を行った際は、コード変更だけでなく以下の関連ドキュメントも**自律的に最新状態へ更新・同期すること**:
    - `basic_design.md`（基本設計書）: 仕様変更、新機能、画面構成、変換仕様等の反映
    - `README.md`: アプリ概要、機能一覧、対応構文、使用例等の反映
    - `PROJECT.md`: 機能インベントリ（Feature Inventory）のステータス更新
- **ルールファイルの自律的見直し・改善**:
  - 開発過程で得られた新たな設計方針、ユーザーからのフィードバックや修正指示、再発防止策などがあれば、**AIエージェント自身が本ルールファイル（`.gemini/rules.md`）を自律的に見直し・追記・改善すること**。
  - ルールファイルやドキュメントを更新した場合は、作業完了時の報告にて「更新・改善した内容」をユーザーに明示すること。
- **プロアクティブな品質改善・リファクタリング**:
  - 作業過程で30〜50行制限の超過、重複コード、日本語コメントの欠落などを検知した場合は、ユーザーからの指摘を待つことなく自律的にリファクタリングを実施して高品質を維持すること。

---

## 6. 品質基準・完了条件
- コード変更後は必ず以下を実行し、エラー0件であることを確認すること：
  1. `npm test`: 全テストスイート（Vitest）がすべて PASS すること
  2. `npm run build`: TypeScript型チェック（`tsc`）および Vite ビルドがエラーなく成功すること
